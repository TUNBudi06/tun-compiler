# QuickTZS — Executor Hardening (opcode permutation + verify self-defense)

Status: pins the format bits BEFORE the first release tag. Two independent features:

1. **Keyed opcode map** — a distributor's executor and its modules share a secret per-build
   permutation of the 2-byte opcode numbers. Obfuscates the bytecode; a module built for one
   distributor is unreadable by any other executor.
2. **Verify self-defense** — the executor refuses to run if its signature/permission check has
   been neutered, and resists casual debugging.

Neither hides anything from the *user*: the signed permission manifest is still shown and
enforced (spec/00, spec/06). These protect the distributor's bytecode and the executor binary
from a *third party*, not the machine owner from the module.

Honesty: on open platforms (Linux, Termux) both are **speed bumps**, not walls. A determined
attacker with the binary wins eventually. The goal is a protection *window*, like commercial
anti-tamper, not permanence. Do not sell either as uncrackable.

---

## 1. Keyed opcode map

### 1.1 Scope (frozen)

Keyed opcodes apply **only to `gen-executor` distributor builds**. Plain `quicktzs build` and the
generic `exectzs` stay on the canonical table (spec/02), so testing, `inspect` and the golden
tests are unaffected. This matches key-mode-2: a keyed module already only runs on its paired
executor.

The canonical opcode table in spec/02 is unchanged and remains the source of truth. A keyed build
is a **private encoding** of that table, not a redefinition (invariant 3 holds: nothing in the
canonical format changes meaning).

### 1.2 The seed (frozen)

- `op_seed`: 32 random bytes, generated by `keygen` and stored inside `identity.tzid` alongside
  the private key. Like the private key, it **never** ships to users and never reaches the build
  server in the clear beyond what key embedding already sends.
- `gen-executor` embeds `op_seed` into the executor through `generated_keys.rs`
  (`pub const OP_SEED: Option<[u8; 32]>`), obfuscated like the other embedded secrets. The generic
  executor template has `OP_SEED = None`.
- The distributor's builder reads `op_seed` from `identity.tzid` when packing, so both sides derive
  the same permutation. No new file, no extra key exchange.

Old `identity.tzid` files (no `op_seed`) stay valid: a missing seed means "not keyed", builds stay
canonical. `keygen` from now on writes a seed; `rotate`/`revoke` keep it.

### 1.3 The permutation (frozen construction)

σ is a bijection on the 16-bit opcode space {0..=65535}, keyed by `op_seed`. Both sides MUST
compute it identically, so the construction is fixed:

```
σ(x):  a 4-round Feistel network on the two bytes of x (L = high byte, R = low byte).
       for round i in 0,1,2,3:
           f  = SHA256(op_seed || [i] || [R])[0]      # one byte
           L' = R
           R' = L xor f
           (L, R) = (L', R')
       σ(x) = (L << 8) | R                            # big-endian 2 bytes on disk
σ⁻¹:   the same rounds run in reverse (Feistel is invertible without inverting F).
```

Feistel guarantees σ is a bijection, so every raw 2-byte value decodes to exactly one canonical
value. Most decode to numbers that are not valid opcodes → the normal "unknown opcode" error, which
also hides which raw values are real.

### 1.4 Builder

When packing with a keyed `identity.tzid`, after codegen the packer rewrites every 2-byte opcode
field `op` to `σ(op)`. **Only the opcode field changes**; operand encoding (var `00 NN`, const
`80|i`, stack `FF`, jump addr 4B — spec/02) is untouched, so instruction lengths and jump addresses
are unchanged. The permutation is applied last, over the final instruction stream, using the opcode
length table so it never touches operand bytes.

### 1.5 Executor

- At startup, if `OP_SEED` is `Some`, build the inverse table `inv: [u16; 65536]` once by iterating
  `c in 0..=65535 { inv[σ(c)] = c }`. ~64k Feistel evals, a few ms, one time. The hot dispatch path
  then does one array lookup `canonical = inv[raw]` before the existing match — no per-instruction
  hashing, so the dispatch speed from the benchmark work is preserved.
- A generic executor (`OP_SEED = None`) that loads a module with `GFLAG_OP_KEYED` set refuses with a
  clear error: `this module was built for a specific executor (keyed opcodes); use that
  distributor's executor`.
- A keyed executor whose seed does not match the module's producer decodes opcodes to garbage and
  fails with "unknown opcode". No seed fingerprint is stored in the module (keeps the format
  minimal); a mismatch is simply an unreadable module.

### 1.6 Dict flag (frozen)

New gflags bit, `GFLAG_OP_KEYED = 1 << 2` (bit 0 = require_online, bit 1 = debug already). Set by a
keyed builder, clear otherwise. `min_exec_ver` stays 1 — keyed builds add no new opcodes, only
relabel existing ones, and are gated by the flag + the paired seed, not by version.

`inspect` on a keyed module (without the seed) shows the flag and reports opcodes as keyed/unknown;
with the matching executor's seed available it disassembles normally. Document that `inspect`
cannot disassemble a keyed module unless given its seed.

## 2. Verify self-defense

The whole promise rests on `verify()` (Ed25519 signature, then the permission check) running
unpatched. The most common crack is forcing it to return "ok". These defenses target that.

### 2.1 Verify self-test (primary; portable, no post-link patching)

Before the executor trusts its own verify path, it runs it against **embedded known vectors** and
aborts if the results are wrong:

- A known-good `(message, signature, pubkey)` triple that MUST verify true.
- A known-bad triple (one byte flipped) that MUST verify false.
- A SHA-256 test vector that MUST match a known digest (detects a patched hash, since the signature
  hash feeds verification).

If the good vector fails, or the bad vector passes, or the digest is wrong, the executor aborts with
a generic error before loading any module. Forcing `verify → true` makes the bad vector pass → abort.
This needs no self-hashing and no two-pass link step, so it works for the recompiled gen-executor
binary. The vectors and the check are obfuscated (obfstr) and the check is inlined into the startup
path, not a single call that is easy to skip.

### 2.2 Anti-attach (speed bump)

- `PTRACE_TRACEME` on self at startup (a second debugger can't attach); if the call shows we are
  already traced, abort.
- Check `/proc/self/status` `TracerPid != 0`.
- Both are easy to bypass (LD_PRELOAD, patch) — they only raise the bar. Off by default is not
  offered; they run in release gen-executor builds and are skipped under `--dev`.

### 2.3 Optional .text integrity (best-effort)

Where feasible, hash the mapped `.text` of the verify functions at startup and compare to a value
the build patches in. Because the recompiled binary makes post-link patching awkward, this is
**optional** and secondary to §2.1; §2.1 catches the main attack without it. Not frozen into the
format.

### 2.4 Boundaries

These treat a *third-party cracker* as the adversary, which aligns with the project. We do NOT add
anti-debug that treats the *machine owner* as the adversary (e.g. refusing to run whenever any
debugger exists on the system) — that contradicts spec/00. `--dev` disables §2.1–2.3 so the
distributor can still debug their own executor.

## 3. What this freezes vs. what can change later

Frozen now (needed before the release tag):
- `GFLAG_OP_KEYED = 1 << 2` in the dict gflags.
- `op_seed` (32 bytes) in `identity.tzid` and `OP_SEED` in `generated_keys.rs`.
- The σ construction in §1.3 (builder and executor must agree forever for a given seed).

Can change later without a format break:
- The verify self-test vectors and anti-debug details (executor-internal).
- The optional .text integrity hash.
- Strengthening σ (e.g. more rounds) — but only as a NEW `op_map` version if ever needed; the dict
  flag would then carry a version. Not needed now.
